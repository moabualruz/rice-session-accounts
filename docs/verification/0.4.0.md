# 0.4.0 verification

Rice Accounts 0.4.0 uses the public plugin API inside ordinary, unmodified
Claude Code. Its activation acceptance uses Claude Code 2.1.301. It requires
neither a replacement launcher nor a preload, native-module patch, proxy or
gateway. The historical 0.3.0 private-adapter proofs do not establish this
version's activation behavior.

## Production public-API proof

`npm run check` runs the Node storage/setup tests, native plugin tests, strict
plugin validation and [proof-public-auth.mjs](../../scripts/proof-public-auth.mjs).
The latter copies the production hooks into an isolated HOME and uses ordinary
Claude processes against a local synthetic Anthropic SDK endpoint. Synthetic
grants are used throughout; it does not access a real account or perform paid
inference.

The proof establishes these behaviors in one native session:

- A's usage is reported at 100%, then selecting B changes subsequent requests
  and selected-account usage to B.
- An agent already running on A uses B on its next request. New agents use B.
- Both public process APIs start ordinary `claude -p` descendants with B.
- A late response started on A cannot replace B's selected-account usage.
- A cached native authorization observed before selection uses B on its next
  first-party request. A cached plugin session reference also follows the
  selected account, and returns to A after `/rice-account login`.
- The real user-entered `/usage` command reports B. A fresh independent process
  retains A, and restoring `login` returns the original process to A.
- Machine settings and account configuration remain byte-for-byte unchanged.

The isolated native tests additionally cover refused environment/state writes,
rollback, credential-read failure and concurrent account changes. An incomplete
rollback latches the session into recovery: model requests, turn dispatch,
public authorization/fetch and child processes are refused until an explicit
selection completes successfully. Internal credential reads remain available
for that recovery.

A regression holds a cached native A reference's credential read while B is
selected, then verifies that releasing the old read cannot fall through to A.
A downstream HTTP refusal is dispatched once with B. The native catch replay
contract was also exercised with an owned fault injected after a settled
downstream call, confirming that its continuation does not duplicate dispatch.

## Interactive reporting and real account checks

An owned ordinary Claude 2.1.301 interactive terminal selected a synthetic B
account, then entered `/status`. It displayed B's email, Max plan and usage,
plus Claude's version, current model and working directory. The persistent
plugin status entry remained on B. The native print frontend rejects `/status`
before plugin dispatch, so print sessions use `/usage` instead.

On macOS, a separately authorized real secondary OAuth grant was selected
through the production `/rice-account` flow inside ordinary Claude. A bounded
native inference succeeded. Both a cached public authorization obtained before
selection and a fresh authorization reached the secondary account's actual
first-party profile with HTTP 200. The machine credential digest and provider
configuration bytes remained unchanged, and the shared config directory was
not replaced. These live checks cover the successful authentication path;
the final isolated regressions cover preparation, race and rollback failures.

`/usage`, interactive `/status`, the persistent account entry and the public
session usage API report the selected account. The plugin does not claim to
rewrite every internal native panel or clear Claude's private credential cache.

## Platform checks and release contents

The CI definition runs compatibility checks on Linux with Claude 2.1.296 and
2.1.299, and on native Windows with 2.1.299. Its current 2.1.301 Linux and
Windows jobs run the full ordinary-Claude public proof; Windows also runs the
native storage/Credential Manager proof. Compatibility checks on an older
engine are not a substitute for the current-engine activation proof.

The macOS local gate covers Node storage/setup tests, native plugin tests,
strict validation and the production public proof. Hosted results are recorded
in the repository's [CI runs](https://github.com/moabualruz/rice-session-accounts/actions).

Release archives exclude the dormant `native/` private adapter and its legacy
launcher proofs through `.gitattributes`. Those files remain available in Git
for historical development evidence, and are absent from the current install
and startup instructions.

# Version 0.3.0 verification

Rice Accounts selects Anthropic OAuth authentication for one session while
preserving its machine configuration, model, plugins, skills and MCP setup.
Version 0.3.0 adds the main-process native cache bridge and managed launcher.
Browser accounts now use their native isolated credential store rather than
being presented as setup tokens.

## Qualified native adapters

| Operating system and architecture | Native Claude Code |
| --- | --- |
| macOS arm64 | 2.1.299, 2.1.300 |
| Linux x64, including WSL | 2.1.296, 2.1.299 |
| Native Windows x64 | 2.1.299 |

Every managed launch checks the selected native executable, embedded module
paths and exact reset-function signatures. Other versions fail with setup
instructions. Setup can save a private official runtime without replacing the
machine's usual Claude executable or updater. Node.js 22 or newer is required;
the Windows development proofs use Node 22.23.3 or newer.

## Actual native SDK proof

`scripts/proof-native-auth.mjs` uses unmodified production account switching,
startup selection and the main-process bridge. It creates an owned plugin copy,
HOME, native credential files and a local HTTP fixture. Anthropic credentials
and responses are synthetic; the native SDK requests, running subagents and
Bash execution are real. It makes no provider request and does not establish
any live account's billing or subscription entitlement.

The proof passed on macOS, Linux and native Windows using native 2.1.299:

- `--account account-a` selects the native store before the first turn.
- An agent sends its first actual Authorization header with account A, then
  pauses in a real Bash tool while the primary session switches to B.
- That same running agent sends B on its next actual SDK request. The primary
  session also sends B.
- Native usage immediately clears A's 18% and 95% limits. B's response supplies
  1% and 2%; a held A response arriving afterward cannot replace those values.
- `login` restores the launch credential environment, including its original
  secure-storage selector. Machine configuration remains selected throughout.

The earlier native 2.1.296 and 2.1.300 reproductions established that SDK account
selection was already correct while native usage retained A's cache. The native
bridge repair was also executed on those adapters. Separate browser-source
probes verified native browser-login classification after a same-process switch.
An owned interactive macOS session reported Chrome enabled, its extension
installed and one browser available. WSL Chrome control is outside this scope.

The same SDK fixture passed through the composed Rice Multi Models launcher,
covering startup account selection and both preloads together. Every fixture
uses owned resources; protected working sessions are untouched.

## Platform and failure recovery

- The managed launcher verifies and saves a fully qualified native executable.
  A plain subsequent launch uses that saved runtime even when PATH contains an
  unsupported Claude version. Missing runtimes, unrelated launcher files and
  failed setup do not silently select another runtime or overwrite saved state.
- Native Windows proofs cover the private preload directory, paths with spaces,
  fallback paths, inherited-ACL refusal, `.cmd` argument transport and plugin
  cache updates. File ownership recognizes the creator token's native owner
  group while retaining the private directory and writer restrictions.
- Native credential-file reads and refresh writes preserve unrelated fields,
  reject stale refresh grants and refuse links or Windows reparse points.
- Windows browser-login folders use protected private ACLs. Setup tokens use
  Windows Credential Manager through stdin, with synthetic Unicode write,
  read and cleanup exercised on the actual platform. The copied terminal
  setup command is tested with spaces, apostrophes and Unicode paths.
- Linux setup tokens use Secret Service. macOS setup tokens use Keychain.
  Browser sign-in uses Claude Code's native storage on every supported OS.

The native process proof also covers both process APIs, Bash, new child Claude
processes, a simultaneous independent sibling and a new independent launch.
These checks preserve machine settings and model selection throughout.

## Reproducing checks

From a checkout with Node and a qualified native Claude executable on PATH:

```sh
npm run check
```

The assembled canonical gate passed 28 Node tests, 81 native plugin tests,
strict native validation, process isolation, actual SDK and launcher proofs.
TypeScript checking passed against generated native 2.1.299 declarations.

On native Windows, set `RICE_ACCOUNTS_PROOF_CLAUDE` to the absolute qualified
native `.exe`, then run:

```powershell
node scripts/proof-windows-bootstrap.mjs
node scripts/proof-windows-storage.mjs
npm run test:windows-launcher
npm run test:auth
```

The repository's [CI workflow](../../.github/workflows/ci.yml) runs the canonical
Linux gate with native 2.1.296 and 2.1.299, plus these native Windows checks with
2.1.299. Browser login and provider entitlement still require the account
owner's actual sign-in; cached identity labels do not replace authorization.
